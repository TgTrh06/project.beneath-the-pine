# Pre-launch core migration baseline

`0000_core_baseline.sql` and `meta/` are generated by Drizzle Kit from the reviewed module schemas. The baseline includes identity/profile, Circle, Pact, focus/session, Open Seed, milestone and allowlisted event storage.

Review the target before explicitly running `pnpm --filter @pyneath/api db:migrate`. There is no admin seed or role bootstrap.

This replaces the identity-only pre-launch baseline. Recreate only an explicitly disposable development database that used the old migration; never apply the replacement as a forward production migration. The implementation did not execute this migration against an existing database.

`0001_white_spacker_dave.sql` is a forward migration adding per-account Circle invitation declines. It has cascading foreign keys to invitation and account, and contains no destructive data change. Review the generated SQL and migration history before applying it. A code rollback can leave the unused table in place; dropping it later would delete recorded decline choices and needs a separate review.

`0002_camp-rename.sql` is the forward-only Circle → Camp contract migration. It renames four enum types, five tables, five foreign-key columns, their constraints and indexes, and three stored product event names. Rows, UUIDs and relationships are retained. Old Circle API clients and `#circle` links are incompatible after this migration; deploy code and migration as one reviewed release. First verify a copy of the old schema with existing rows and a fresh database. Do not run this against the user's local database or a pilot/production database as part of repository validation. A rollback to old code requires a separately reviewed reverse migration or a restored backup; code-only rollback is unsafe.

`0003_account-preferences-and-pact-reminders.sql` adds account preferences and one reminder receipt per account/Pact. Existing accounts use off/empty defaults without a backfill. Both tables cascade on account deletion; receipts cascade on Pact deletion. Review this forward migration and backup before any real-data rollout. Dropping these tables during rollback would lose saved choices and reminder history.

`0004_personal-forest-milestones.sql` adds a private account/threshold table constrained to 1, 3 and 7, with account deletion cascade. It does not rewrite session history. The personal memory endpoint materializes qualifying historical milestones on first read using original completion dates. A code rollback can leave this unused table in place; dropping it loses memories and requires separate review. Implementation validation applies this migration only to disposable test databases, never the existing local/pilot/production database. See ADR-0026.

On 2026-11-03, the user separately authorized applying `0003` and `0004` to the existing local `btp_review` database after backup and verified restore. This dev rollout is complete; see [rollout evidence](../../../docs/07-testing/personal-forest-dev-rollout.md). This does not authorize applying migrations to another environment.

`0005_personal-forest-arrangement.sql` adds layout, hidden-item array and an independent forest version to `account_preferences`, with P1-compatible defaults and database constraints. It preserves existing preference values and account-deletion cascade. After disposable-database validation, the user separately authorized the dev rollout on 2026-11-03: a fresh backup was restored and verified, 0005 was tested on that copy, then applied to `btp_review`. Dev is now at 0005 and live integration checks passed. Apply schema before restarting the new API in any separately approved rollout. A code rollback may keep the added columns and migration journal; dropping them loses saved arrangements and requires separate review. See [ADR-0027](../../../docs/04-engineering/adr/0027-personal-forest-arrangement.md), [implementation verification](../../../docs/07-testing/personal-forest-p2a.md) and [dev rollout evidence](../../../docs/07-testing/personal-forest-p2a-dev-rollout.md).
